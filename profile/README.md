> You shouldn't fit your company to the software.

**EmpoweredHouse is the runtime that turns your process into your software.**

This organization is where the runtime lives in public. The scaffold, the primitives, the process repository tooling, and the observability layer underneath: open by default, generated by AI in the loop, governed before the first line of bespoke code ships.

We build software shaped to a company's actual work, not configured to fit a generic shape. Code is a liability, not an asset. The win is less code, shaped exactly to the process it serves. AI gave that conviction new leverage. We made it the substrate.

---

### The argument, in one paragraph

For two decades, the smartest companies stitched their operations together from other people's software. Configuration consultants got rich. Quarterly contracts decided what the company could and could not do. The stack ran the business.

That era ended when AI collapsed the cost of bespoke code from quarters to hours. The question is no longer which SaaS do we buy. The question is what does our operating system look like, and who owns it.

EmpoweredHouse is the runtime that lets your company answer that question. Generated, not configured. Owned, not licensed. The work decides the shape.

---

### Shape. See. Run.

The lifecycle is three beats.

You **shape** the software your company runs on, inside a runtime that takes command of governance, compliance, security, and execution.

You **see** your company in motion through an intelligence layer that knows what its objects mean: [shugyo.ai](https://shugyo.ai).

Your business **runs** on what you shaped.

This GitHub organization carries the substrate beneath the first beat. The second beat lives at shugyo.ai. The third lives at your company, in code you own.

### What lives here

Two public repositories carry the runtime today. The rest is incubating in private or sold as product.

| Repository | Function |
|---|---|
| [`process-native-starter`](https://github.com/EmpoweredHouse/process-native-starter) | The `pns` CLI that bootstraps a Process Native project. Generates a Phoenix umbrella with LiveView and LiveReact, wires the AI engineering harness (progressive-disclosure AGENTS.md, decision records, GSD workflows, community skills), and ships with CI quality gates (Credo, ESLint, Sobelow, Dialyzer, coverage, E2E). The substrate the bespoke layer is built on. |
| [`accrete`](https://github.com/EmpoweredHouse/accrete) | Compound knowledge for AI-native development. Decision records (SDR, PDR, ADR) as version-controlled, MCP-searchable infrastructure backed by a Kuzu graph database. Each decision makes the next decision easier. The context-engineering layer that lets agents and humans see why the code was built the way it was. |

[Shugyo](https://shugyo.ai) is the intelligence layer over the running business. Sold as product, not open here. Its signal contract and integration points will land in this org as the ecosystem matures.

The remaining layers of the runtime (primitives library, full process repository tooling, runtime observability, the process-mapping playbook as a standalone package) are incubating. Watch this org or talk to us if you need them sooner.

A competent technology leader should be able to find this profile, run `pns init`, and start. Without ever talking to us. If that is not true, we are holding the open source hostage.

### The default stack

Elixir and Phoenix. The runtime, the team's training, and our recruiting pipeline are aligned to it. `process-native-starter` encodes the default: Phoenix umbrella + LiveView + LiveReact + React 19 + Tailwind v4 + ShadCN, with the harness wired in. A different stack is accepted only when a hard constraint demands it. The burden of proof sits with the deviation, not with the default.

We pick the default deliberately. An ecosystem becomes a sequence of unrelated custom projects the moment the stack is chosen engagement-by-engagement.

### How to start

Without us:

```bash
bun install
bun run build
bun link

pns init \
  --project-slug my-app \
  --otp-app my_app \
  --module-name MyApp \
  --product-name "My App" \
  --client-name "Client Name"
```

You get a Phoenix project with the harness in place, decision records wired through `accrete`, and the GSD workflow ready to plan and execute the foundation milestone. See the [QUICKSTART](https://github.com/EmpoweredHouse/process-native-starter/blob/main/QUICKSTART.md) for the full path.

Reach out at [empowered.house](https://empowered.house). The first conversation is the mapping.

## Editorial notes

For internal use when this README is updated.

### Voice guardrails

- No emojis. No em dashes (the brand book bans them; use colons, semicolons, commas, parentheses, or separate sentences).
- "Runtime" stays lowercase. Claimed by usage, not typography. Same move as AWS owning "the cloud."
- Never call EmpoweredHouse an "agency" or a "platform." Never refer to the customer's output as "our software."
- Verb shift enforced: shape, own, generate, build, hold, decide. Avoid: configure, license, subscribe, buy, rent, adapt.

### Surface mapping

This README serves the recruiting motion first, the build-in-public marketing motion second, the adoption-without-our-push motion third. In that order.

- Recruiting: engineers find us through the code, not through a job ad. The tone is direct and technical; the bar is implied by the standard of the repositories linked.
- Marketing: every repo in the table is a public commitment. The org page is the index of those commitments.
- Adoption: the "How to start, without us" path is load-bearing. If it ever stops working, the ecosystem stops compounding.

### Update triggers

Refresh the repository table when:

- A repo moves from private to public.
- A new layer of the runtime ships (primitives library, runtime observability, process repository tooling, mapping playbook as a standalone package).
- The default stack changes (a high bar; do not edit casually).
- A sector pattern reaches the threshold for its own repo.
- The Shugyo signal contract or integration points land in the org.

Do not edit the position, the trinity, or the tagline without going through [[claim-system]].
